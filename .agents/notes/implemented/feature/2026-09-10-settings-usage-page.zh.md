# Agent Note: 设置页「用量信息」

Status: implemented

[English](2026-09-10-settings-usage-page.md) | 中文

## Problem

提供方发布两个账户事实，却不发布任何费用数字。`GET /user/balance` 报告还剩多少；每个补全应答报告自己用了多少 token。两者都回答不了「花了多少、按时间、按模型拆开」—— 而每个应答里的用量是一次性的，之后再取不到。

Harness 其实早已记录了自己花的每一个 token：`assistant/message` 事件携带提供方用量，`dsh-token-meter` 把它们折叠成每会话的 `tokenUsage` 投影。只是没有任何东西跨会话去读它，因此用户能看到一个会话的缓存命中率，却看不到上周花了多少。平台控制台确实有一张消费图，但它是登录态单页应用，数据走私有 XHR；要消费它就得把用户的控制台会话塞进 agent 运行时，而凭据规则禁止这样做。

## Decision

设置里新增一页 **用量**，读取一个新的 Remote 命名空间，渲染四块内容：账户余额、消费曲线、按模型的 token 折线，以及其下的按模型明细表。

**三个主机包加一个线端所有者。** `@deepseek-ai/dsh-usage-ledger` 把已提交的会话事件折叠成持久的每会话账本。`@deepseek-ai/dsh-deepseek-balance` 执行账户级读取。`@deepseek-ai/dsh-balance-ledger` 保存那些让消费可被推导出来的读数。`@deepseek-ai/dsh-api-usage-controller` 拥有 `usage` Remote 命名空间，自己不拥有任何数据。浏览器包 `@deepseek-ai/dsh-client-ui-settings-usage` 注册该页，并且不重复计算主机已经决定的任何东西。

**用量账本不是 session projection。** 它在自己的 `usage_ledger` 域中每会话存一条记录。做成投影就必须发布 wire 值，而 `api/session-controller/src/list.ts` 会为每个被列出的会话发送每一个已注册投影的 wire 值；按小时、按路由的负载比那条路径今天携带的值大好几个数量级。

**桶是 UTC 小时，且两个维度都带时间。** 每个存储的小时自带该小时的路由拆分。按路由的生命周期总量回答不了带窗口的问题 —— 半年前用过一次的路由会出现在「最近 7 天」的图里。窗口以两个绝对时刻过线，因为把小时归并成本地日需要读者的时区，而时区不是主机持有的事实。

**存储记录携带继续折叠所需的全部信息**：已折叠到的序列号、当时生效的路由，以及仍可能被重述的那次尝试。持久化该样本，正是让「重启恰好落在流式样本与最终消息之间」变得精确、而不仅仅是「不太可能出问题」的原因。

**消费是差值，符号就是全部的分类依据。** 用量只会让余额下降，因此两次读数之间的下降就是消费，上升只可能是充值或退款。账本原样保存水平量，把分类留给浏览器；本地日的归属也归浏览器：一个区间记在它**后一次**读数所在的日，因为那是它被观察到的时刻。

**读余额这个动作本身就记录它。** Remote 把 `balance` 经由账本，因此页面执行的读取本身就是曲线所依据的样本。绕开账本的读取会在用户看过的地方正好留下一个洞。

## Alternatives considered

**把用量账本做成 session projection。** 很地道，还能白拿投影缓存的检查点。它输在负载：会话列表 Remote 会为每个被列出的会话携带按小时、按路由的值。这个替代方案的另一半是给列表加键过滤，它输在允许清单将不得不枚举未来任何功能注册的每一个 wire 投影。

**用配置的单价表而不是读数推导消费。** 能给出精确的每会话、每模型成本，也不需要采样。它输在价格页是文档而不是 API：表是「模型 × 峰谷 × 三档」，会随时变动，而一张错的表会静默地报出错误的钱数。读数在总量上不可能错，只可能错在「什么时候」。

**单个全局账本文档。** 比每会话一条记录简单。它输在每个事件都要重写整个文档，而「一种币种一条序列」并不是一个按会话推进的折叠的自然写入单位。

**假设 UTC 日界。** 比发送时刻区间便宜 —— 客户端可以只问「最近 7 天」这个数字。它输在 UTC 的一天在北京时间 08:00 开始，而日桶一旦写下就无法再切分，因此这个错误会永久留在存储数据里。

**超过八条序列后循环调色板。** 这样每个模型都能画出来。它输在重复颜色会被读成同一条序列，那比把尾部合并成一条「其他模型」更糟。

## Consequences

token 数字只覆盖本 Harness 自己发出的请求，而余额与消费曲线覆盖整个账户 —— 两块面板的差额恰好就是本 Harness 从未产生的那部分用量，页面如实说明而不是强行对齐。消费曲线只有起点没有史前：没有 API 提供余额历史，因此它只能从采样开始的地方起。采样缺口整块落在恢复采样那天。赠金过期与用量无法区分，因为提供方优先扣减赠金，使拆分的两半同时变化。

账本最初的设计持久化一个「安全水位」，只在没有尝试处于报告中途时推进。该水位永远无法越过一个流式样本，导致几乎什么都写不进去 —— 这是被单元测试抓到的，而不是在生产里，之后改为持久化「未闭合的样本」与「当时生效的路由」。

Typert 生成器拒绝这样的 Remote 签名：其返回类型经由本包自己的再导出跨包；类型必须在签名使用它的地方以显式的包导入写出。每个新包还需要手写它自己的 `/types` 子路径别名，因为别名生成器只产出包根与 `/invariant`。

## Testing

单元 spec 覆盖：折叠的尝试内替换与保留期、账本与控制器的窗口裁剪与零路由省略、解码器对畸形余额体的拒绝、采样器对失败读取拒绝记录、两个符号方向的余额差分分类，以及图表在「某模型只有会被该口径忽略的流量」时仍然过滤掉它。区块的 spec 直接喂 store，并断言读者对某一份答案看到的内容。
